### মূল কারণ

**discover (কোড পড়ে বের করা):**

1. `ohsogo.com` মিনিটে একটা অনুরোধে বাঁধা (`workers/stores/index.ts`-এর `pace(host, 60_000)`), তাই ৩০ মিনিটে ~৩০টা পাতা পড়ে `finished: false` দেয়।
2. `summarize()` শুধু সব দোকান `finished` হলে `markDiscovered()` ডাকে (`workers/jobs/discover.ts`)। একটা দোকান শেষ না হলে কোনো পণ্যই চিহ্ন পায় না।
3. পরের run-এ `plan` আবার সব দোকান চালায়, আর `discoverStore()`-এর `done` শর্ত pending পণ্যের পাতা আগে পড়া থাকলেও বাদ দেয় না। তাই সব দোকান একই পাতা আবার পড়ে।
4. OHSOGO নিজেও প্রতিবার তালিকার প্রথম ~৩০টা পাতাই পড়ে, তাই কখনো শেষ হয় না।

**prices:**

1. সরাসরি পড়ার ধাপ ১৫ মিনিটে বাঁধা (`DIRECT_MINUTES`), আর সবচেয়ে বড় দোকানের (Apple Gadgets, ৪৩০ পাতা × ২ সেকেন্ড) জন্য পুরোটাই লাগে।
2. Jina fallback ধাপ তার **পরে** শুরু হয়ে ৩২ মিনিট পর্যন্ত চলে (`FALLBACK_MINUTES`)। অর্থাৎ ~১৭ মিনিট শুধু অপেক্ষার ক্রমের কারণে।
3. ৬টা ধীর দোকান (সবগুলো Shopify, `product: shopifyProduct`) প্রতি run-এ মাত্র ~১৫টা পাতা পড়তে পারে।

## ২. QA: আগের প্রস্তাবের কোন অংশ টিকল, কোনটা টিকল না

আসল `price_history`, `offers` আর দোকানের sitemap দিয়ে পরীক্ষা করা।

| প্রস্তাব | ফল | প্রমাণ |
|---|---|---|
| discover-এর বারবার পড়া বন্ধ | ✅ টিকল | ১৭৬ পণ্য ৮ দিন ধরে আটকে; কারণ কোডে স্পষ্ট |
| Shopify bulk (`/products.json`) | ✅ টিকল | custommacbd, ohsogo, istockbd তিনটাতেই HTTP 200, এক অনুরোধে ২৫০ পণ্য, `robots.txt` আটকায় না |
| Jina fallback আলাদা করা | ✅ টিকল | কোডে ধাপ দুটো পরপর, একসাথে চালাতে বাধা নেই |
| Backoff (৪→২৪ ঘণ্টা) | ⚠️ দাম আছে | ১৪ দিনের সিমুলেশন: পড়া ২০%-এ নামে, কিন্তু দাম বদল ধরতে মাঝারি দেরি ১৬ ঘণ্টা |
| Sitemap `lastmod` সংকেত | ❌ বাদ | Apple Gadgets-এ ৭১টা আসল দাম বদলের মাত্র ৩৮টায় (৫৪%) `lastmod` নড়েছে; Motion View-এ ২টার ০টায় |
| জনপ্রিয় পণ্যে ছোট বিরতি | ❌ বাদ | `page_views`-এ গত ৭ দিনে `product_id`-সহ সারি ০টা, ভিত্তি করার ডেটা নেই |

**আগের দুটো ভুল দাবি, শুধরে নেওয়া:**

- "মাত্র ০.৭% দাম বদলায়" ছিল এক run-এর হিসাব। আসলে ৩ দিনে ১৪%, ১৪ দিনে ৪৭% অফারে অন্তত একবার দাম বদলেছে, আর বদলগুলো নানা অফারে ছড়ানো (১৪ দিনে ২+ বার বদলেছে মাত্র ৪০০টা)। তাই backoff "বিনা খরচে" নয়।
- "বাকি ৩২৬টা আটকানো দোকানের" ভুল। বেশিরভাগই ৬টা ধীর Shopify দোকানের।

**Backoff-এর মাপা হিসাব (১৪ দিন, ৫৪৯২ অফার):**

| বিরতির সিঁড়ি (ঘণ্টা) | এখনকার তুলনায় পড়া | দেরি: মাঝারি / ৯০% / সর্বোচ্চ |
|---|---|---|
| এখন (সব ৪ ঘণ্টায়) | ১০০% | ০ / ০ / ০ |
| ৪, ৮, ১২ | ৩৫% | ৬.৬ / ১০.৩ / ১২ ঘণ্টা |
| ৪, ৮, ১৬, ২৪ | ২০% | ১৬.৪ / ২৩.৫ / ২৪ ঘণ্টা |

## ৩. ধাপ

### ধাপ ০: শুরুর মাপ রাখা (কোড নয়)

নিচের সংখ্যাগুলো টুকে রাখুন, শেষে একই জিনিস আবার মেপে তুলনা হবে:

- `job_runs` থেকে শেষ ৩টা `prices` আর `discover` run-এর সময় আর বার্তা।
- pending পণ্য: `select count(*) from products where discovered_at is null or discovered_at < discover_requested_at;`
- ৬টা Shopify দোকানের প্রতিটায় মোট কয়টা পণ্য (`/products.json?limit=250&page=N` খালি না আসা পর্যন্ত, প্রতি অনুরোধের মাঝে ৬০ সেকেন্ড, worker-এর নিজের user-agent দিয়ে)। ১২ নভেম্বর জানা: istockbd ১৯৯টা (১ পাতা), sneakerzone ২৩৯টা (১ পাতা), custommacbd ২৫০+, splayd ২৫০+, ohsogo-র ৪টা product sitemap (অর্থাৎ হাজার কয়েক)। ragen এখনো গোনা হয়নি। এই মাপ দিয়েই ধাপ ২-এ কোন দোকানে bulk চালু হবে তা ঠিক হয়।

### ধাপ ১: discover দোকান-প্রতি অগ্রগতি

**লক্ষ্য:** একটা ধীর দোকান বাকিদের আবার চালায় না; কোনো দোকান একই পাতা দুবার পড়ে না।

**১ক. Migration** (`npm run db:new discover-per-store`; মালিক নিজে `npm run db:push` চালাবেন, এজেন্ট নয়):

```sql
alter table sellers add column discovered_at timestamptz;
update sellers set discovered_at = (select max(discovered_at) from products);
```

backfill-এর কারণ: `null` থাকলে প্রতিটা দোকান পুরো ক্যাটালগ নতুন করে খুঁজত। এই মানে শুধু এখনকার pending ১৭৬টা আরেকবার খোঁজা হবে।

**১খ. `workers/services/sellers.ts`:** `SellerRef`-এ `discoveredAt: string | null` যোগ, `sellersByStore()`-এর select-এ `discovered_at`। নতুন ফাংশন `markStoreDiscovered(sellerId, startedAt)`।

**১গ. `workers/jobs/discover.ts` → `discoverStore()`:**

- শুরুতেই `const startedAt = new Date().toISOString()`।
- `since` না থাকলে `pending` = যে পণ্যের `requestedAt > (seller.discoveredAt ?? "")`। নতুন দোকানের নিয়ম (`known.size === 0` হলে পুরো ক্যাটালগ) আগের মতোই।
- শেষে, `since` না থাকলে আর `result.finished` হলে `markStoreDiscovered(seller.id, startedAt)`, দুটো ব্যতিক্রম ছাড়া:
  - আটকানো (`blocked`) দোকানেও চিহ্ন **বসে**; ঘরের runner ওদের দেখে। নইলে এখনকার ৬টা আটকানো দোকান (Electronics Bangladesh, Glowella, Onix, Skyland, Smart Deal, Umrelo) প্রতি run-এ আবার চলত।
  - দোকান-স্তরের অন্য ত্রুটিতে (বাইরের `catch`-এ ধরা, `blocked` নয়, যেমন তালিকা আনায় `fetch failed`) চিহ্ন বসে না।
  - পাতা-প্রতি ব্যর্থতা (`result.failed`, প্রতি run-এ ৫–২৫টা) চিহ্ন আটকায় না; নইলে একটা খারাপ পাতার জন্য দোকান বারবার চলত।
- `since` থাকলে (লোকাল runner) কিছু বদলাবে না।

**১ঘ. পড়া পাতা মনে রাখা** (`workers/stores/listings.ts`-এ, নতুন ফাইল নয়):

- `.cache/listings/<store.id>.done.json`: `{ [url]: handledAt }`।
- `discoverStore()`-এ কোনো listing বাদ যায় যদি তার `handledAt` ওই listing-এ মেলা সব pending পণ্যের `requestedAt`-এর পরে হয়। পণ্য আবার চাওয়া হলে (ভার্সন বদল) পাতা আবার পড়া হয়।
- `handle()` ত্রুটি ছাড়া শেষ হলে URL-টা লেখা হয়; `StoreBlocked` বা অন্য ত্রুটিতে নয়।
- `discover.yml`-এর cache ধাপ আগে থেকেই `.cache/listings/*.json` জমায়, তাই workflow বদলাতে হবে না। যাচাই করুন `hashFiles` নতুন ফাইলটাও ধরছে।

**১ঙ. `workers/jobs/matrix.ts` → `plan()`:** দোকান চালু হয় শুধু যদি কোনো পণ্যের `requestedAt` তার `discoveredAt`-এর পরে হয় (`discoveredAt` খালি হলে সবসময়, তাই নতুন দোকান নিজেই আসে)। `catalog.some((p) => p.pending)` আর ব্যবহার হবে না। "একটাও দাম নেই" নিয়মটা **বাদ**: read-only simulation-এ দেখা গেছে তাতে ৪টা আটকানো দোকান (umrelo, electronicsbangladesh, smartdeal, onix) চিরকাল প্রতি run-এ আসত।

**১চ. `summarize()`:**

- `markDiscovered()`-এর শর্ত থেকে `results.every((r) => r.finished)` বাদ; শুধু `results.length === expected`। সময়ে শেষ না হওয়া দোকান এখন নিজের `discovered_at` দিয়েই পরের বার ফেরে। `products.discovered_at` থাকছে কারণ অ্যাডমিন আর `docs/agent-workflow.md`-এর `search_done` এটা পড়ে।
- শুরুর দিকের error ছোড়ার শর্ত (`results.every((r) => r.notes.length > 0)` আর নতুন দাম ০) থেকে শুধু "সময়ে শেষ হয়নি" নোটের দোকান বাদ। কারণ: ধাপ ১-এর পর অনেক run-এ শুধু OHSOGO চলবে, তার নোট থাকবে "শেষ হয়নি" আর নতুন দাম ০ হতে পারে। তখন এখনকার শর্তে run error হয়, আর error `markDiscovered()`-এর আগে বলে pending কখনো ০-তে নামে না।

**যাচাই:**

- ধাপ ১-এর পর প্রথম run: সব দোকান একবার চলে। দ্বিতীয় run (নতুন পণ্য ছাড়া): `plan`-এর `stores` আউটপুটে শুধু যারা শেষ করেনি (প্রত্যাশা: শুধু `ohsogo`)।
- OHSOGO-র বার্তায় প্রতি run-এ নতুন পাতা পড়া হচ্ছে, আর কয়েক run পরে সে তালিকা থেকে বাদ পড়ে।
- একটা পরীক্ষার পণ্যে `update products set discover_requested_at = now() where id = '...'` দিলে পরের `plan`-এ আবার সব দোকান আসে, আর আগে পড়া পাতাও আবার পড়া হয়।
- pending গোনা ০-তে নামে।

### ধাপ ২: Shopify দোকানে এক অনুরোধে অনেক দাম

> **১২ নভেম্বরের পরীক্ষার পর বাদ রাখা।** ঘরের IP থেকে read-only তুলনা (worker-এর user-agent আর ৬০ সেকেন্ড বিরতি মেনে, দোকানগুলো ৩০ সেকেন্ড ফাঁকে শুরু): ৫টার ৪টা (istockbd, custommacbd, sneakerzone, ragen) প্রথম `/products.json` অনুরোধেই 429; worker-এ একটা 429 মানে পুরো run-এ দোকান আটকানো, এখনকার চেয়ে খারাপ। একই দোকানে একা, থেমে পাঠালে 200 আসে। splayd চলেছে: ৯৮৮ পণ্য, ৪ অনুরোধ, মেলানো পণ্যে দাম হুবহু এক, কিন্তু আমাদের ১০টা লিংকের মাত্র ১টা তালিকায় ছিল। আবার ভাবতে হলে আগে GitHub-এর IP থেকে একই পরীক্ষা, আর লিংক কেন তালিকায় নেই তা দেখা।

**লক্ষ্য:** ৬টা ধীর দোকানে মিনিটে-একটা পাতার বদলে পুরো তালিকা কয়েক অনুরোধে।

**`workers/stores/parsers.ts`:**

- নতুন `shopifyCatalog(origin)`: প্রতি origin-এ একবার (memoized promise), `getJson(`${origin}/products.json?limit=250&page=N`)` যতক্ষণ ২৫০টা আসে। ফল `Map<handle, ShopProduct>`।
- `shopifyProduct(url)` আগে এই map দেখে; handle না পেলে বা তালিকা আনা ব্যর্থ হলে এখনকার `/products/<handle>.js` পথে যায়।
- `StoreBlocked` আগের মতোই ওপরে ছোড়া হয়। জেনে রাখুন: তালিকা আনায় একটা 429 এলে `checkStatus()` পুরো run-এর জন্য দোকান আটকানো ধরে, তখন ওই দোকানের সব পাতা Jina-তে যায়। ১২ নভেম্বর খালি `Mozilla/5.0` user-agent দিয়ে ৪টা দোকানই প্রথম অনুরোধে 429 দিয়েছে, `DordamBot` দিয়ে 200; তাই user-agent আর `pace` ছোঁয়া যাবে না।

**`products.json` আর `.js`-এর পার্থক্য (ভুল হওয়ার জায়গা):**

| ঘর | `.js` (এখন) | `products.json` |
|---|---|---|
| `price`, `compare_at_price` | সংখ্যা, পয়সায় (÷১০০) | লেখা, টাকায় (`"122000.00"`) |
| `options` | নামের তালিকা বা `{name}` | `[{ name, values }]` |
| ছবি | `featured_image` | `images[0].src` |
| `available` | আছে | আছে (১২ নভেম্বর যাচাই) |

**কোন দোকানে bulk:** চালু অবস্থায় পাতা গুনে সীমা ঠিক করা নয়। মিনিটে একটা অনুরোধে ৮ পাতা আনতে ৮ মিনিট যায়, তারপর বাদ দিলে OHSOGO প্রতি prices run-এ ~১৫টার বদলে ~৭টা পাতা পড়ত, discover-এও একই ক্ষতি। তার বদলে `Store`-এ একটা চিহ্ন (যেমন `bulk: true`), ধাপ ০-র মাপ দেখে শুধু সেই দোকানে যাদের তালিকা ৮ অনুরোধের মধ্যে আসে (২০০০ পণ্যের কম)। OHSOGO-তে নয়; তার জন্য ধাপ ১-ই সমাধান। `shopifyCatalog()` শুধু চিহ্ন থাকা দোকানে ডাকা হয়।

**যাচাই:**

- `npm run worker:check` (বা একটা read-only স্ক্রিপ্ট): একই ১০টা handle-এ `.js` পথ আর bulk পথের `rows` (অপশন, দাম, পুরনো দাম, স্টক) হুবহু এক।
- পরের `prices` run-এর পর custommacbd আর istockbd-র ৮ ঘণ্টার বেশি পুরনো দাম ১৩৯ আর ৫৫ থেকে ০-র কাছে নামে।
- ওই দোকানগুলোতে নতুন `HTTP 429` বা `blocked` নোট নেই।

### ধাপ ৩: Jina fallback সরাসরি পড়ার সাথে একসাথে

**লক্ষ্য:** `prices` run থেকে ~১৫ মিনিট কমানো, দামের টাটকা ভাব একটুও না কমিয়ে।

**`workers/jobs/prices.ts` → `refreshPrices()`:**

- `blocked` এখন একটা সারি; fallback-এর লুপ সরাসরি ধাপের **সাথে** চলে (`Promise.all`), সারিতে কিছু এলেই তুলে নেয়।
- লুপ থামে যখন সরাসরি ধাপ শেষ **আর** সারি খালি, অথবা `fallbackDone()`।
- fallback-এর ভেতরের ক্রম বদলাবে না: আগে `jinaRead`, না পেলে `aiRead`, একটা একটা করে।
- `FALLBACK_MINUTES` ৩২ থেকে কমিয়ে ২২; `TOTAL_MINUTES` ৩৮ থেকে ২৮। `DIRECT_MINUTES` ১৫-ই থাকে।
- `tally`-তে দুই লুপ একসাথে লেখে; Node এক থ্রেডের বলে আলাদা lock লাগে না, কিন্তু `await`-এর মাঝখানে পড়ে-তারপর-লেখা (`x = x + n`) নয়, `+=` সরাসরি।

**যাচাই:**

- run-এর সময় ৩২–৩৮ থেকে ২২–২৮ মিনিটে (fallback ২২ মিনিট পর্যন্ত, তারপর `autoVersions`/`autoReview` ২৮ পর্যন্ত)। fallback-এর কাজ আগে ফুরালে আরও কম।
- বার্তায় "Jina-র সার্ভার দিয়ে পড়া" সংখ্যা আগের সমান বা বেশি (১৮৪–২২৯)।
- "দেখেছে" সংখ্যা কমেনি।

### ধাপ ৪ (ঐচ্ছিক, মালিকের সিদ্ধান্ত লাগবে): backoff

ধাপ ১–৩-এর পর আবার মেপে তারপর সিদ্ধান্ত। এটা না করলেও ওপরের লাভ থাকে।

- **কখন করবেন:** দোকান 403 দিয়ে আটকানো বাড়লে, বা Apple Gadgets-এর ১৪ মিনিট কমাতে চাইলে।
- **দাম:** ধাপ ২-এর টেবিল। সুপারিশ `৪, ৮, ১২` (পড়া ৩৫%, মাঝারি দেরি ৬.৬ ঘণ্টা); `২৪` পর্যন্ত নয়।
- **কীভাবে:** `offers`-এ `next_check_at timestamptz` আর `unchanged_checks smallint`; `refreshOffer()` দাম **বা স্টক** বদলালে গোনা শূন্য করে, নইলে বাড়ায়; `refreshPrices()` শুধু `next_check_at <= now()` সারি আনে, `next_check_at` ধরে সাজিয়ে। ব্যর্থ আর "ভার্সন মেলেনি" সারিও পিছিয়ে দিতে হবে, নইলে ওরা প্রতি run-এ সবার আগে আসে।
- মালিক "হ্যাঁ" না বলা পর্যন্ত শুরু নয়।

## ৪. যা করা যাবে না

- প্রতি দোকানে ২ সেকেন্ডের বিরতি, একসাথে একটাই অনুরোধ, `robots.txt` মানা আর নিজের user-agent বদলানো নয়।
- ধীর দোকানের `pace(host, 60_000)` কমানো নয়, bulk পথেও।
- Proxy বা একাধিক IP দিয়ে দোকানের সীমা পাশ কাটানো নয়।
- Sitemap `lastmod` দিয়ে পাতা বাদ দেওয়া নয় (ওপরে মাপা: ভরসার নয়)।
- নতুন টেবিল, status পাতা, alert বা অ্যাডমিন UI যোগ নয়; শুধু যা এখানে লেখা।
- `supabase db push` বা লেখার `db query` এজেন্ট চালাবে না; মালিককে কমান্ড দিন।
- লোকাল runner-এর (`local_discover`, `local_prices`) আচরণ বদলানো নয়।
- বাড়তি কমেন্ট নয়; এখনকার ফাইল আর ফাংশন বাড়ান, নতুন স্তর নয়।

## ৫. প্রতিটা ধাপের পর

1. `npm run typecheck`, `npm run lint`, `npm run build`।
2. `npm run worker:dry`।
3. আলাদা commit, বাংলা বার্তা আগের ধারায় (`fix:` / `feat:`)।
4. ধাপ ১-এ migration আগে push (মালিক), তারপর কোড; উল্টো হলে `sellers.discovered_at` না পেয়ে `discover` ব্যর্থ হবে।
5. `main`-এ push মানেই deploy (`rebuild`)।
6. শেষে [12-workers-cron](features/12-workers-cron.md)-এ কী বদলাল লিখুন, `docs/index.md`-এর ট্র্যাকারের ১২ নম্বর সারি হালনাগাদ করুন, আর এই ফাইলের অবস্থা বদলান।
